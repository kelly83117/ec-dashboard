## 0. 開工前的兩件事

### TEST_NOWRITE（最重要）

#### 🔴 測前必做：先單獨確認 guard 已生效（放在所有本機測試步驟的最前面）

**任何會寫入的本機測試之前**，先在 F12 Console **單獨執行**這一行、看它回 `true`：

```js
window.__TEST_NOWRITE_ON === true
```

- 回 `true` → guard 生效，可以測。
- 回 `false` 或 `undefined` → **立刻停手**，guard 沒貼（或沒生效），先照下面把防護碼貼進 `js/firebase.js`、重載、看到紅字，再回來重跑這行確認。

⚠ **這個檢查一定要「獨立執行」**：先單獨貼這一行、確認 `true`，**才能**接著做會寫入的操作。**不可以**把它跟寫入動作（存對帳、按同步、上傳套用…）寫在同一段腳本／同一次貼上——合在一起就等於「沒把關」：真值是 false 時，寫入照樣先跑了。

⚠ **最容易漏的時機＝「合併完 → 下次測試」之間**。guard 刻意不 commit，所以**每次合併都會把它剝掉**；下次要測時 `firebase.js` 裡沒有 guard、`__TEST_NOWRITE_ON` 是 `undefined`。
根因是**拆除與貼回不對稱**——「測完拆除」下面有明確步驟、清單、順序；「下次測前貼回」以前沒有任何步驟，靠人記，所以常漏。這一段就是補上那個不對稱的缺口：**拆除有步驟、貼回也必須有一步（就是先跑上面這行）**。

---

本專案前端直連正式 Firestore，**沒有測試環境**。`js/app.js` 把 `Store.set` patch 成「寫入即同步正式庫」，所以**在本機起 server、光是載入頁面就會寫公司資料**。

要在本機測試，必須先把 TEST_NOWRITE 防護碼貼進 `js/firebase.js`：

- 位置：`window.dispatchEvent(new Event('cloudStoreReady'));` **之前**（此時 17 個 `__cloud*` 物件都已建好，掃得到）
- 用這個錨點找，不要記行號
- 貼 F12 主控台無效（patch 閉包已捕獲原物件）

**開 App 第一件事看 Console，要有紅字「TEST_NOWRITE v2 已啟用：17 個物件 / 25 個寫入方法已停用」**，才能測。

- **判斷標準是物件數**：目前 **17 物件 / 25 方法**（2026-09-16 實測；`table` 57 條屬性＝25 攔截＋31 放行讀取＋1 非函式，另 forKey 包裝 1 條）。
- ⚠ **物件數會隨新增 cloud 物件而變，當場重數**（`grep -nE "^\s*(window\.)?__cloud[A-Za-z0-9_]*\s*=" js/firebase.js`）。**數字對不上就停下來查是哪個物件沒被掃到，不要因為「比預期多」就當作沒事**——少於預期＝有寫入路徑沒被擋（保護有洞）；多於預期＝有新物件，要確認它的寫入方法也被 no-op 且已補進 MUST。
- ⚠ **guard 的 `MUST` 明列清單要跟著新增的 cloud 物件一起維護**：MUST 是 fail-loud（動態掃描抓不到「應該存在卻不存在」，靠 MUST assert throw）。新增 cloud 物件時，把它的寫入方法同步補進 MUST，否則新物件沒有 fail-loud 保護。
- 動態掃描下限已設「至少 17」，低於就 throw（原本「至少 6」等於沒有下限）。
- ⚠ **與唯讀角色防護共存**：`js/app.js` 的 `__installReadonlyCloudGuard` 會在 `cloudStoreReady` 後再包一層（只在 role='view' 時攔）。因 TEST_NOWRITE 先跑、它包到的是 no-op，所以**即使不是 view 角色寫入仍被擋**（可打 `window.__TEST_NOWRITE_HITS` 看攔截紀錄佐證）。用 `.toString()` 看方法會看到外層唯讀 wrapper，別誤判成沒生效。

commit 時只 `git add` 實際改動的檔案，**不要 `git add -A`**，避免夾帶測試碼。

### 版本號 15 處（用 `bump-version.js`，不要手動改）

改任何檔案（**含 CSS**）都要 bump，漏掉同事會拿到舊版。共 **15 處**：

- `index.html` 的 `<meta name="app-version">`（1）
- `index.html` 的 `<script src="js/main.js?v=">`（1）
- `index.html` 的 **3 個 CSS `<link ... ?v=">`**（main.css / profit.css / daily-adjustments.css）← 早期漏列的就是這 3 個；**動到 CSS 一定要一起 bump，否則 `version.js` 只清 Cache API、碰不到瀏覽器 HTTP 磁碟快取，CSS 餵回舊的（v226→227 血淚）**
- `js/main.js` 裡 10 個 import 的 `?v=`（10）

**用 repo 根目錄的 `node bump-version.js <新版號>` 一鍵改全部 15 處＋自動 grep 驗證，不要手動逐一改**（`--check` 可先看現值/一致性）。

不要憑記憶抓號碼，`--check` 或搜 `app-version` 看現況；新號要比檔案裡的、也比 `main` 上的都大（main 會回退，不保證遞增）。

> ⚠ 版號 bump 的**時機**依 CLAUDE.md 版號規則：動到 runtime（js/css）的改動走「本機原子合併」——feature 分支不 bump，合併進 `main` 後才在 main 上跑 `bump-version.js`＋commit＋push（merge 與 bump 同一次 push，零部署空窗）。

## 1. PChome 是什麼模型

**供貨商模式，不是平台抽成模式。** PChome 向我們買斷、再自行定價賣出，對帳單上寫「貴公司應開發票金額」——發票是我們開給 PChome 的。

結構上**與 momo 甲配同構**：

| | momo 甲配 | PChome 一般轉單 |
|---|---|---|
| 營收基準 | 未稅進價 × 對帳數量 | 未稅供貨價 × 數量 |
| 平台抽成 | 無 | 無 |
| 倉租 | 無 | 無 |
| 費用來源 | 對帳單實際金額 | 對帳單實際金額 |

**→ 實作時先讀甲配那段的既有程式碼，沿用同一套框架，不要另起爐灶。**

**沒有 % 手續費、沒有類別抽成。** 對帳明細 16 個項目全部展開，沒有任何依營收比例計算的抽成欄位；供貨模式的平台獲利內含在售價與供貨價的價差裡。**不要為「3% 手續費 / 類別抽成」寫任何計算邏輯。**

### 費用結構＝每月固定費 ＋ 少量變動費（2026-09 定案）

實際查證（2026-09 對帳單）PChome 的 (D) 費用長這樣：

| 類型 | 項目 | 本期金額(含稅) | 性質 |
|---|---|---|---|
| **固定費** | 系統服務費 1000 ＋ 活動贊助費 1000 ＋ 獎勵金合約 1000 | 3,000 | 每月幾乎固定（在 (D4) 行銷獎勵金段的子項表） |
| 固定費 | (D11) 產品責任險 | 100 | 每月固定、**只在對帳單、CSV 沒有** |
| 變動費 | (D4) 行銷推廣費（逐筆檔期活動） | 272 | 隨檔期，逐筆掛 SKU |
| 變動費 | (D1) 退貨物流費 · (D2) 罰金 · (D5) 簡訊費 | 90 / 0 / 39 | 隨當月出貨/退貨/申訴 |

**規模效應（固定費被營收攤薄）**：固定費約 3,100/月幾乎不動，所以**有效費率隨營收下降**——月營收 5 萬 → 約 8.8%、10 萬 → 約 5.7%、30 萬 → 約 3.6%。這是「固定費 ÷ 營收」的算術結果，不是抽成級距。**衝量能明顯壓低單位費率**。

**淨利費用歸屬模型（`pchomeProfitCalc`）**：
1. **逐筆歸該 SKU**：罰金（(D2) 依商品編號）＋行銷推廣費（(D4) 變動子項逐筆）＋退貨物流費（(D1) 逐筆）＋簡訊費（見 §9 甲公式）。
2. **攤提池 ＝ 固定費 ＋ 產品責任險 ＋ 對不到料號的費用**，按各 SKU **max(淨營收,0) 比例**攤（最大餘額法，殘差補給營收最大那支 → Σ攤提 === 攤提池）；零銷／負營收不攤。
3. 逐列費用（未稅）＝(罰金＋行銷推廣＋退貨物流＋簡訊＋攤提) ÷ 1.05。**守恆：Σ逐列費用含稅 ＋ 未分攤 === (D) 總額**（`pchomeProfitCalc` 有 console assert；2026-09 實測 3,501／未稅 3,334、未分攤 0、差 0）。
4. 折讓單 **(B1)/(C1) 當費用、不扣營收**（定案①；本期 B=C=0）。

目前**只做一般轉單，不做寄倉**。寄倉相關的 6 個費用項（包材費、倉儲費、倉庫作業處理費、進貨退出運費、安裝費、分攤運費(寄倉商品)）不會有值。

## 2. 資料來源：對帳明細匯出檔

### 檔案格式陷阱

副檔名是 `.csv`，但實際上：

- **編碼：UTF-16LE**（含 BOM）
- **分隔符：Tab**，不是逗號
- **一個檔案含 16 個區段**，每段自己一組標題列 → 標準 CSV parser 讀不了，必須先做區段切分

|---|---|---|
| 0 | 訂單貨款明細 - 一般轉單 | (A1) |
| 1 | 訂單貨款明細 - 寄倉訂單 | (A1) |
| 2 | 退貨貨款明細 - 一般轉單 | (A2) |
| 3 | 退貨貨款明細 - 寄倉訂單 | (A2) |
| 4 | 退貨貨款明細 - 寄倉客退商品(退回廠商) | (A2) |
| 5 | 其他應付 | (A3) |
| 6 | 行銷獎勵金(貴公司已開折讓單) | (B1) |
| 7 | 專案獎勵金(貴公司已開折讓單) | (C1) |
| 8 | 退貨物流費 | (D1) |
| 9 | 罰金 | (D2) |
| 10 | 分攤運費(寄倉商品) | (D3) |

### (D4) 行銷獎勵金段的內部結構（`pchomeBuildMarketingSeg`）

(D4)/(D12) 獎勵金段不是單純一個總額，內部有兩種版型，解析器要都認得：

- **subitem 版**（本期 (D4)）：總額列下有一張子項迷你表（欄＝「系統服務費-應付金額 / 活動贊助費-應付金額 / 獎勵金合約-應付金額 / 行銷推廣費-應付金額」四欄的表頭＋值列）。判定：某子項名在後面的**明細區塊有對應「…-應付金額」欄** → 當**變動費**（逐筆有 SKU）；否則當**固定費**（進攤提池）。本期 = 固定 3000（系統服務費/活動贊助費/獎勵金合約 各 1000）＋ 變動 行銷推廣費 272（5 筆逐列 52/105/24/72/19）。
- **account 版**（本期 (D12)）：「科目／金額」兩欄式，無子項迷你表；整段當攤提（本期 0）。
- **一致性檢查**：`Σfixed+Σvariable vs 總額`、`各變動子項逐筆 Σ vs 值列`，對不上 → 差額進 `unallocatable`（攤提池）＋ `warnings`（月對帳頁不靜默）。
- **HTML entity**：行銷活動名稱等文字欄含 `&#NNNN;`／`&#xHHHH;`／具名實體 → `pchomeDecodeEntities` 解碼（數值欄不解碼）。
- (D11) 產品責任險**只在對帳單、CSV 沒有段** → 由貼上解析寫進 `對帳單.明細.D11`，計入攤提池；沒貼對帳單時它落入未分攤（即時模式）。

## 3. 口徑定義

### 營收

**營收（未稅）= 應付金額 ÷ 1.05**

`應付金額` 是含稅（對帳單 (A) 欄位明寫「應開發票金額(含稅)」）。`單位成本` 是 PChome 的進貨價，也就是我們的供貨價——**不是我們的成本**。

`成本小計 = 單位成本 × 數量`，`應付金額 = 成本小計 − 團購折扣`。

### 退貨（A2 退貨貨款）— 2026/09/30 定案

**過去的 bug**：`pchomeProfitCalc` 只讀段0（訂單貨款 A1），**退貨貨款段（A2）從不讀** → 營收/銷量/成本都是 gross、退貨沒扣。實測 2026-09：營收 9,828.57（應為對帳單 A 未稅 9,509、差 320＝336÷1.05）、DEBWN3 銷量算 3（應 2）。量級 3.4% 營收，跨期會累積。

**修法（逐筆，不是從總額扣）**：段2 退貨貨款逐筆 → 用 `商品編號 → 料號`（pnToCode(段0) 否則商品主檔）對映到 SKU：
- **營收**：該 SKU 淨營收 −= 退貨應付 ÷ 1.05。→ **驗收硬條件：總營收未稅 === 對帳單 A 未稅**（本期 9,509）。
- **銷量**：該 SKU 淨銷量 −= 退貨數量。（DEBWN3 2 件、非 3）
- **成本**：退貨成本**沖回**（`PCHOME_RETURN_COST_REVERSAL = true`）。使用者確認 PChome 退回的貨實務上可以再上架販售，所以退回那件不計入銷貨成本，`成本 = unitCost × 淨數量`。**這是業務事實不是技術選擇**；若日後退貨品質變差、多數不能再上架，改常數為 `false` 即可切換成 gross 數量計算。（2026/09/30 使用者確認）**只有這一個常數控制、不散落各處。**
- **歸期**：認在**退貨出現的那一期**（照對帳單 A2，不回頭改前期）。首要是能跟對帳單對上。
- **對不到料號**：記 `returnUnattributed`（警示、不靜默丟）。
- **對帳卡連動**：`(A) vs CSV 貨款` 的 csvHuo 也要淨扣退貨（段0 − A2），否則會誤報「差＝退貨額」。

**負營收列（前期賣、本期退 → 淨營收/淨銷量 ≤ 0）處理**：
- `hasBiz`（本期有售）用**淨值正向**判定：只有退貨（淨 ≤ 0）**不算有售** → 淨利率顯「—」、不進動銷率分子、不除以 0。
- 負數照 `pchomeMoney` 的 `-$X` 格式顯示；該列仍計入合計（讓合計＝對帳單 A）。
- 攤提（費用模型 PR）用 `max(淨營收, 0)` 當權重，負營收列攤提 0。

### 成本

**沿用甲配做法：建檔時**以 `廠商料號` 查 `ec_momo_cost_by_origin`（查不到的手動填），把查到的值**寫進 `product.cost` 凍結**。**計算時直接讀 `product.cost`，不做 live 查詢。**

⚠️ 為什麼建檔時查、不 live 查：PChome 成本要人工乘好入數（見下），live 查會讓「成本表改了但入數沒重乘」悄悄傳播到歷史報表；建檔時寫死，歷史數字凍結。（甲配實作同此：`momoAddOriginLookup` 在建檔輸入原廠編號時查表寫入 `product.cost`，`momoAggregatePeriods` 計算時只讀 `product.cost`。）

⚠️ **成本表存的就是「PChome 這一件的成本」，程式不做任何入數換算。** 多入裝商品（例：`水槽過濾網-200入` 對應成本表 100 入 × 2）的倍率在填表時就乘好，程式直接取用。

**不要寫倍率欄位、不要寫換算邏輯。**

唯一的防護是顯示層：成本欄位旁顯示供貨價/成本比值，異常高的比值（8 倍以上）代表可能忘了乘，**只標示不阻擋**。

🔴 **成本的真正持久層是共用表，這點不直觀、務必記住**：`product.cost` 是**凍結的快取值**，成本的權威持久層是**共用的 `ec_momo_cost_by_origin`（＋ `ec_momo_cost_meta` 記人工/來源）**，跟 momo 共用。手動 ✎ 改成本（`pchomeMasterCommit`）會同時寫 `product.cost` 與 `momoSetCostByOrigin(manual, src:'PChome')`。**重傳上架清單時 `product.cost` 會從共用表 `momoLoadCostByOrigin()` 重查回填**（查不到才保留既有），所以**手動成本不會因重傳而遺失**。→ 因此商品同步**不需要**另做一套「人工成本保護 / protected[] 彈窗」，共用表機制已經在保護。唯一會弄丟成本的情況：商品從清單消失被**整筆刪除**（就是下面在修的 bug）。

### 商品同步：合併，不是整份覆蓋（2026-09-30 起，PR 待補）

上架清單上傳 (`pchomeListingFile`) 從「整份覆蓋」改成**合併 + 差異預覽 gate**。修的 bug：舊的整份覆蓋會把「這次清單沒有的商品」整筆刪掉，`product.cost` 一起消失 → 該 SKU **過去期別的淨利算不出來**（calc 讀 `product.cost`、不 live 查共用表）。

**新增兩個欄位**（形狀非破壞、舊記錄缺席有安全預設）：
- `source`: `'listing'`（來自上架清單）｜`'manual'`（批次維護手建、第 6 步才會有來源）。**現有記錄無此欄 → 視為 `'listing'`**。
- `lastSeenExport`: 字串，該筆**最後一次出現在上架清單時的匯出時間**（`pchomeExportTime` 格式「YYYY/MM/DD HH 時」，固定寬度→字串比較即時序）。

**下架狀態用戳記推導、不存 boolean**（自我修復、免維護、能知道是哪版清單後消失）：
- `pchomeLatestExport(products)` ＝ 全部 `listing` 來源記錄的最大 `lastSeenExport` ＝ 目前最新清單版本。
- `pchomeVanished(p, latest)` ＝ `source!=='manual'` 且 `p.lastSeenExport` 存在 且 `!== latest`。
- calc 的 `discontinued` ＝ `!pchomeIsActive(p) || pchomeVanished(p, latest)`。總表「顯示已下架」toggle 讀的還是 `discontinued`，顯示層不動。
- 🔴 **`lastSeenExport` 缺席 → 不推導為消失**（現有 329 筆全都沒有此欄；否則第一次同步會把全部誤標下架）。第一次上傳只會給「這次在清單裡」的品打上戳記，不會 flag 任何消失。

**合併規則**（`pchomeApplyListingMerge`）：
- 清單有、本機沒有 → 新增，`source:'listing'`、`lastSeenExport=本次匯出`。
- 兩邊都有 → 只更新 `PCHOME_LISTING_FIELDS`（商品名/規格/商品編號/供貨價/售價/毛利率PC/可賣量/缺貨/出貨方式/shop/商品狀態）＋ `cost` 從共用表重查 ＋ `lastSeenExport=本次匯出`；**不碰**其他我方欄位。
- 本機有、清單沒有 → **保留整筆、不更新 `lastSeenExport`**（於是被 `pchomeVanished` 推導為消失、標下架）；`source:'manual'` 者連消失都不推導（手建品不會因沒上架就被標下架）。

**差異預覽 gate**（`pchomeRenderListingPreview`，照 momo 視覺語彙）：解析後**不直接寫**，先顯示新增 N／更新 N（列出變更欄位 舊→新）／消失 N（標下架）／保留未標 N（舊記錄無戳記）→ **確認才 `pchomeApplyListingMerge`**、取消什麼都不寫。寫入仍走既有 `pchomeSaveProducts`（localStorage＋_mem＋_profitMem＋_markPending＋pchomeDirtyAdd），雲端覆蓋仍由既有「☁ 同步雲端」的「雲端較新」把關，**不另開寫入路徑**。

**歷程（per-product history）這次不做**：PChome 目前沒有任何東西會編輯商品本體（成本改動已記在 `ec_momo_cost_meta` 的 `changes[]`），為 329 筆各加歷程陣列會撐大上雲文件；**留到第 6 步批次維護**跟優化紀錄／工作日誌一起做。這次只確保資料形狀不擋住之後加歷程。

**⚠ 備份**：這支合併後，使用者第一次在正式站按同步＝新合併邏輯第一次跑真實資料。動工前已把正式站 `ec_pchome_products`（329 筆）匯出備份：`C:/Users/victo/Downloads/PChome儀表板檔案/ec_pchome_products_backup_20260930_174827.json`。**第一次在正式站按同步前，先確認這個備份檔還在。**

### 費用

**全部是對帳單實際金額，沒有任何費率需要推算。** 不要建費率模型。

費用同樣是含稅，計算淨利時除以 1.05。

歸屬規則：

- **罰金**——明細有 `商品編號`，歸屬到 SKU
- **其餘費用項**——沒有 SKU 明細，列為「未分攤費用」，只進合計不進個別商品

**不要照營收比例分攤罰金。** 罰金是特定商品的營運事故，攤到其他商品會讓淨利率失真（這與 MO+ 的 feeB 按同單營收比例分攤不同，那是真正的共同費用）。

因為有未分攤費用，**各列淨利加總不等於合計**，要有獨立一列讓兩邊對得起來。

## 4. 匯入規則

### 快照覆蓋，不能累加

**這是最容易出錯的一條。**

同一個帳務週期會被重複匯出，內容不同：

| 匯出時間 | 列帳日期區間 | 資料列 | 貨款 | 罰金 |
|---|---|---|---|---|
| 2026/09/08 | 2026/08/26 ~ 09/25 | 2 | 365 | 115 |
| 2026/09/16 | 2026/08/26 ~ 09/25 | 21 | 5973 | 0 |

期間完全相同。而且**罰金申訴成功後會被改寫成 0**，代表歷史資料是可變的。

**→ 以「帳務月」為主鍵（＝列帳日期區間起始日正規化），後匯入完整覆蓋先前。絕對不能 append。** 重傳一次就翻倍是這個功能最可能的 bug。

⚠️ **主鍵用「帳務月」不是完整區間字串**（教學修正）：後台「本期」結束日會隨當天變動（教學截圖 `本期(2025/08/26~2025/09/02)`），但 CSV 匯出的區間字串是完整月區間（實測兩份都是 `2026/08/26 ~ 2026/09/25`）。為防未來變動，主鍵用**起始日正規化成帳務月**（週期 26→25，起始月 M → 帳務月 M+1，如 `2026/08/26` → `2026-09` 期）。起始日不同才算不同期，不要用完整字串比對。

### 期別歸屬

帳務週期是 **08/26 ~ 09/25**，不是自然月。每列**用 `單號確認日` 歸到自然月**（教學修正，見下），與甲乙配的期別維度一致，**不需要為 PChome 開獨立期間軸**。

⚠️ **歸期依「單號確認日」，不是「轉單日期」**（教學 p.7 修正、會算錯期）：教學原文「依單號確認日落在【列帳日期區間】內之訂單，列入該期帳務」「廠商完成出貨回填後…確認出貨單號無誤時即產生單號確認日」。實測落差常達兩天（`20260827201081-01` 轉單 08/27／確認 08/29；`20260913416211-02` 轉單 09/13／確認 09/15），期間內看不出、但月底交界（9/24 轉單、9/26 確認）會歸錯期。**calc 與月對帳的歸期一律讀 `單號確認日`；`轉單日期` 只在訂單明細顯示、不作歸期依據。**

本期未結束時不要算成長率，標示「本期未完」。

### 訂單分組

`訂單編號-序號` 的格式是 `<14位訂單號>-<2位序號>`。

**group key = 最後一個連字號之前的部分。**

序號會跳號，這是正常的——PChome 一張訂單可混多家廠商，我們只拿得到自己那幾序。實際樣本裡有 `-03`、`-10`、`-06`、`-04` 單獨出現的情形，**不要當成資料缺漏去補**。

同單多序範例：`20260909326564-01/-02/-03`（腰帶三色），出貨單號同為 `677172815185`。

### 料號對應

`廠商料號` 是**規格層級**的鍵，可直接查成本表，不需中間對照表。

PChome `商品編號` 的尾碼對應規格：

```
DIAECY-A900KE6PT-003 → D27-02  (軍綠)
DIAECY-A900KE6PT-004 → D27-01  (黑色)
DIAECY-A900KE6PT-005 → D27-11  (藏青)
```

`單位成本` 在全期內每個料號都一致，沒有逐單浮動。

## 5. UI 規格

## 7. 風險結構（影響優先級判斷）

這條線的獲利特性與其他通路不同：

| | |
|---|---|
| 毛利率 | 75~83%（實測兩支） |
| 平台費率 | 0% |
| 主要風險 | **出貨延遲罰金** |

罰金 115 元一次 ≈ 吃掉該商品 93.6% 的毛利。罰金明細有 `罰金天數` 欄位，代表**按天累計**。一筆漏單的總損失（罰金 + 錯失毛利）約 238 元，相當於兩件的獲利。

**→ PChome 這條線不需要在費率、定價上著墨，該投資的是出貨狀態的可見度。** 之後若要加功能，「有罰金的訂單」比「低毛利商品」更值得做。

## 9. 還未驗證的部分

以下都**沒有實際樣本**，不要預先實作：

- **退貨**——兩期皆為 0。退貨明細欄位含 `入帳日期`，若與原訂單 `轉單日期` 錯開，歸期邏輯需另議
- **分攤運費(轉單超取)**——含 `溫層` 欄位，可能有冷藏/冷凍差別費率
- **廣告費 / 行銷獎勵金 / 專案獎勵金**——折讓單性質，與貨款是不同的會計流向
- **罰金計費規則**——單一樣本反推疑似「零售價 × 50%」（229 × 50% = 114.5 ≈ 115），**未經證實，不要寫進程式碼**

### 簡訊費推算規則（已實作為「推算」，非事實）

從 (D5) 簡訊費明細頁（對帳單每個 (D) 項旁的「檢查」連結）推出：簡訊分六類（新增訂單／取消訂單／出貨通知／對帳通知／換貨通知／借貨通知）。實測本期只有「新增訂單」＋「取消訂單」。

**規則（甲公式，2026-09-30 定案改此）：簡訊費 ＝ 出貨明細計費筆數 × 1 元（含稅）**
＝ 段0（訂單貨款）**有出貨單號的明細列數** ＋ **退貨物流費筆數**。

- ⚠ **是「計費筆數」不是簡訊封數**。一箱一出貨單號、同一訂單多序號共用單號；PChome 按明細列計費，不是按不重複訂單。
- **驗證（2026-09 完整期別、精確吻合）**：出貨明細列 38 ＋ 退貨物流 1 ＝ **39**，與對帳單 (D5)=39 **完全相符**（舊「不重複訂單數」公式只得 32、對不上）。
- **實作**：`pchomeProfitCalc` 回 `簡訊費推算{列數, 退貨物流筆數, 推算, 含稅, 未稅}`；並回五個自驗欄 `smsEstimate / smsShipLineCount / smsReturnLogisticsCount / smsReturnGoodsCount / smsActualD5`。**逐筆掛該列 SKU**（計入逐列費用、計入合計，即時模式標推算）。月對帳頁「簡訊費 核對」列顯示 推算 X／實際 (D5) Y／差 Z。
- **三個但書（UI 已標）**：
  1. **單價 1 元未經 PChome 公告**，只有單一樣本反推佐證。
  2. **取消訂單簡訊算不出來**（取消的訂單不在對帳明細裡）→ 推算**偏低**。
  3. **有實際 (D5) 時一律以實際為準**（貼上解析取得），推算退居核對用並顯示差額。
- ⚠ **PChome 若改價或新增簡訊類型，這條規則要重驗。**

### 費用雙狀態（即時／已對帳）——為什麼轉單模式的即時推算可接受

**問題**：對帳單每月 26 號才開放，不可能等對帳單才知道當月狀況。**先例**：momo 甲配在對帳單未到時本來就用 `estFeeRate`（近 3 月均費率或 6.8%）暫估費用（`momoAggregatePeriods` L11698-11701）＋狀態晶片「⚠ 未對帳」＋橫幅——「期中用估計值」在本專案早有先例。

**PChome 的雙狀態**（`pchomeProfitCalc` 回 `feeState`）：

| 狀態 | 觸發 | 費用 | 標示 |
|---|---|---|---|
| **即時** | 對帳單未貼上 | CSV (D) 組實際 ＋ **簡訊費推算**（計入合計、標推算） | 期別旁 `.mm-status no`「未對帳」；`.mm-banner-warn` 說明簡訊甲公式＋**「只在對帳單、CSV 沒有的費用（如產品責任險 D11）此時未計入 → 淨利可能略偏高」** |
| **已對帳** | 貼上對帳單 (D) | 對帳單 (D)（權威、含 D11 責任險） | `.mm-status ok`「已對帳」；feeChip tooltip 顯示推算與實際 (D5) 差額 |

**為什麼即時值可接受**：轉單模式**0% 平台抽成**，(D) 費用裡罰金／退貨物流費／行銷推廣費／固定費（(D4) 子項）**CSV 本來就有區段**，簡訊費用甲公式逐筆推算（本期精確＝39）。**CSV 唯一拿不到的是「只在對帳單」的項**——主要是 (D11) 產品責任險（本期 100/月固定）；即時模式它未計入 → 費用略低、淨利略高，貼上對帳單即補齊（本期即時 (D) 3,401 vs 已對帳 3,501，差＝責任險 100）。

🔴 **刻意不做 `estFeeRate` 那種 %比例暫估**：轉單模式沒有比例費，加了只會變成沒人知道要填什麼的空欄位。推算標示一律用 `.mm-banner-warn`，不自創樣式。

## 10. 專案既有慣例（照做）

- 開工前 `git pull`（main 很活躍，會回退）
- 樣式寫進 `css/`，不用 inline style
- 純手寫 HTML + CSS + 原生 JS，**沒有建置流程，不能用需要編譯的語法**
- 跨檔呼叫走 `window`，模組結尾要 `Object.assign(window, {…})` 掛回去——**忘了掛，按鈕會 ReferenceError 靜默失效**
- 一次只做一塊，做完驗過再做下一塊
- 改完要在瀏覽器實際點過才 commit
- push 前先 `git fetch` + `git log --oneline HEAD..origin/main` 防撞，有輸出先 merge
- 用 merge 不用 rebase
- push 完直接開 PR 直接合併，中間不要跑去做別的事

### PChome 專屬（2026-09-16 起，一律適用）

- **一律先在 localhost 開給人測、驗過才 push 才上正式站。** 不要寫完直接 push、不要「小改動所以直接上」。每完成一塊就把 server 起著、給網址 + 要測什麼，對方實際點過再往下。
- 交 server 前，**自己先看一次 Console 確認 TEST_NOWRITE 生效**（見 §0）——localhost 點到的任何東西都不能寫進正式 Firestore。
- **測完拆除順序（勿顛倒）**：先關分頁 → 再停 server → 最後才刪防護碼。反了會「檔案沒保護但瀏覽器記憶體還是舊的」，重整就寫正式庫。
- 刪完 `git diff js/firebase.js` 應為空；commit 只 `git add` 實際改動的檔案，**不要 `git add -A`**（免夾帶測試碼）。
